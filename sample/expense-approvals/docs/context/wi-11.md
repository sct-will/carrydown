### architecture 3.5 Routing

The routing engine builds the steps when a report moves from Submitted to In approval. It uses the base total of the report.

| Base total (USD) | Steps in order |
| --- | --- |
| Up to 500.00 | Line manager |
| 500.01 to 5,000.00 | Line manager, department head |
| 5,000.01 to 25,000.00 | Line manager, department head, finance reviewer |
| Above 25,000.00 | Not routed. The service returns E_LIMIT and the submitter follows the offline exception process. |

Rules that apply to every route.

1. If an approver in a step is the submitter, that step moves to the next person up the reporting line.
2. Steps are decided in order. A later step does not see the report until the earlier step approves.
3. A reminder goes to the current approver after 3 business days without a decision. After 5 business days the step escalates to the next person up the reporting line, and the audit trail records the escalation.
4. The routing result is stored as approval_step rows and does not change after routing, except by escalation.

### architecture 3.6 Deployment

The service runs as one container behind the company gateway, in three environments: test, staging and production. Database migrations only move forward. The export job runs at 02:00 UTC and writes to the ledger drop folder. The whole feature sits behind the flag EXPENSE_APPROVALS_ENABLED (section 5.1). With the flag off the service starts, answers its health check and refuses every other request with the status 404.

### architecture 4.2 GOV-2 Audit and retention

Owner: internal audit. Applies to every table named below.

1. Every state change of a report writes one audit_event in the same database transaction. If the audit write fails, the change fails.
2. The audit table is append only. The application account has insert and select rights on it and no update or delete right.
3. An audit_event records who, when, what changed (from_state and to_state), and a small detail object. It holds identifiers, never names, receipt contents or email addresses.
4. Reports, line items, approval steps and audit events are kept for 7 years from the decision date. Receipt files are kept as long as their report.
5. Deletion happens only by a retention job after the 7 years, and never for a report under a legal hold.
6. Log lines carry report identifiers and event types. They never carry amounts, comments or receipt contents.
7. Reading the audit trail of a report is itself recorded as an audit_event of type audit.viewed.

### architecture 5.1 DS-1 Delivery standard

Owner: the platform engineering team. Applies to every pull request.

1. Feature flag. All new behavior sits behind EXPENSE_APPROVALS_ENABLED, off by default. With the flag off, nothing observable changes except the health check.
2. Tests. `npm test` runs the unit tests. `npm run test:contract` runs the contract tests against `contracts/openapi.yaml`. Both pass before a pull request merges.
3. Lint. `npm run lint` passes with no warnings.
4. Contracts first. `contracts/openapi.yaml` is the interface between the Workflow track and the Experience track. A change to it is its own pull request, announced at the next checkpoint.
5. Migrations. `npm run migrate` applies migrations. They only move forward. Each has a test that runs it on an empty database and on a copy of the previous schema.
6. Errors. Every error response uses the envelope of section 7.1.
7. Pull requests stay under 400 changed lines where possible. The description lists the acceptance criteria and the proof for each.
8. Commit messages are in the imperative mood. Secrets and personal data never appear in code, tests, logs or fixtures.

### architecture 7.3 Ledger export file

One file per night, named `expenses-YYYYMMDD.csv`, with a second file `expenses-YYYYMMDD.sha256` that holds the SHA-256 checksum of the first. One row per approved line item of every report that moved to Approved since the last export. After writing, the job moves those reports to Exported.

| Column | Meaning |
| --- | --- |
| report_id | UUID of the report |
| line_item_id | UUID of the line item |
| employee_id | Submitter |
| cost_center | Cost center of the submitter at approval time |
| spent_on | Date of the expense, YYYY-MM-DD |
| category | Category code |
| amount_cents | Amount in the line currency, integer |
| currency | ISO 4217 currency code |
| base_amount_cents | Amount in USD, integer |
| approved_at | UTC timestamp of the last approval |

### architecture 8.1 Risks

| Id | Risk | Response |
| --- | --- | --- |
| R1 | The reporting line data is out of date, so routing picks the wrong manager. | Routing reads the line once at submit time and records it. Finance can ask for a re-route. |
| R2 | Managers ignore reminders and reports pile up. | Escalation after 5 business days (section 3.5). The pilot measures time to decision. |
| R3 | The export format changes after finance review. | The file format sits in one module and a contract test. The stakeholders own the sign-off. |
| R4 | Receipts hold personal data. | Receipt store keys are random. Receipts are never logged or put in events (GOV-2). |
| R5 | The two tracks drift on the API. | Contracts first (DS-1.4) and a joint check at every checkpoint. |

## Conflict resolution that applies

- Section 3.5 rule 4 says steps do not change after routing except by escalation, and R1 says finance can ask for a re-route. Section 7.1 has no re-route endpoint. The ground truth does not define the path, so the runbook says what the service does today and names the stakeholders as the owners of the gap.
- The business analyst note asks for a reminder after 2 business days and section 3.5 says 3. The work items use 3. The runbook and the R2 review must say 3, and the next version of the architecture document should settle the number.
