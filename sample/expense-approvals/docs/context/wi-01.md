## Obligations

### architecture 3.1 Overview

One service with one database, a receipt store, a message queue for notifications and a nightly export job.

```text
Web client --> API gateway --> Expense API --> PostgreSQL
                                   |  \--> Receipt store (object storage)
                                   |
                                   +--> Queue --> Notification worker --> Email
                                   |
                       Export job (02:00 UTC) --> Ledger drop folder
```

### architecture 3.2 Components

| Component | Owner track | Purpose |
| --- | --- | --- |
| Web client | Experience | Report form, receipt upload, approver inbox, delegate screen. |
| Expense API | Workflow | REST API of section 7.1. Validates, stores, routes, decides. |
| Routing engine | Workflow | Builds the ordered list of approval steps for a report (section 3.5). |
| Rules module | Workflow | Applies the limits and separation of duties of GOV-1 on every decision. |
| Audit writer | Workflow | Appends events to the audit table (GOV-2). |
| Notification worker | Experience | Reads queue events and sends the emails of section 7.2. |
| Export job | Workflow | Writes the nightly ledger file (section 7.3). |
| Receipt store | Workflow | Holds receipt files. Keys are random and never derived from names. |

### architecture 3.3 Data model

All identifiers are UUIDs. All timestamps are UTC. Amounts are integers in minor units (cents). A fixed rate table, maintained by finance and loaded as data, converts a line item currency to the base currency (USD).

| Table | Key fields |
| --- | --- |
| report | id, submitter_id, state, base_total_cents, submitted_at, decided_at, version |
| line_item | id, report_id, spent_on, category, amount_cents, currency, base_amount_cents, merchant, note |
| receipt | id, report_id, line_item_id (optional), object_key, content_type, size_bytes, sha256 |
| approval_step | id, report_id, position, role, approver_id, state, decided_at, comment |
| delegate | id, approver_id, delegate_id, starts_on, ends_on |
| audit_event | id, occurred_at, actor_id, report_id, event_type, from_state, to_state, detail (JSON) |

### architecture 3.6 Deployment

The service runs as one container behind the company gateway, in three environments: test, staging and production. Database migrations only move forward. The export job runs at 02:00 UTC and writes to the ledger drop folder. The whole feature sits behind the flag EXPENSE_APPROVALS_ENABLED (section 5.1). With the flag off the service starts, answers its health check and refuses every other request with the status 404.

### architecture 5.1 DS-1 Delivery standard

Owner: the platform engineering team. Applies to every pull request.

1. Feature flag. All new behavior sits behind EXPENSE_APPROVALS_ENABLED, off by default. With the flag off, nothing observable changes except the health check.
2. Tests. `npm test` runs the unit tests. `npm run test:contract` runs the contract tests against `contracts/openapi.yaml`. Both pass before a pull request merges.
3. Lint. `npm run lint` passes with no warnings.
4. Contracts first. `contracts/openapi.yaml` is the interface between the Workflow track and the Experience track. A change to it is its own pull request, announced at the next checkpoint.
5. Migrations. `npm run migrate` applies migrations. They only move forward. Each has a test that runs it on an empty database and on a copy of the previous schema.
6. Errors. Every error response uses the envelope of section 7.1.
7. Pull requests stay under 400 changed lines where possible. The description lists the acceptance criteria and the proof for each.
8. Commit messages are in the imperative mood. Secrets and personal data never appear in code, tests, logs or fixtures.

### architecture 7.1 REST API

All paths start with `/v1`. All bodies are JSON. The caller's identity comes from the gateway header `X-Employee-Id`, which the gateway sets and clients cannot forge.

| Method and path | Purpose | Success |
| --- | --- | --- |
| POST /reports | Create a draft report. | 201 with the report |
| GET /reports/{id} | Read a report with line items, receipts and steps. | 200 |
| PUT /reports/{id} | Replace the line items of a draft or returned report. | 200 |
| POST /reports/{id}/receipts | Upload a receipt (multipart form). | 201 with the receipt |
| POST /reports/{id}/submit | Submit a draft or returned report. | 202 with the state |
| GET /inbox | List the reports waiting for the caller, oldest first. | 200 with a page |
| POST /reports/{id}/decisions | Approve, reject or return. | 200 with the report |
| PUT /delegates | Create or replace the caller's delegate record. | 200 |
| GET /reports/{id}/audit | Read the audit trail (auditors only). | 200 with a page |

Decision request.

```json
{ "decision": "approve", "comment": "" }
```

`decision` is `approve`, `reject` or `return`. `comment` is required and not blank for `reject` and `return`.

Error envelope used by every endpoint.

```json
{
  "error": {
    "code": "E_FORBIDDEN",
    "message": "GOV-1.3 refused this decision: the approver already decided an earlier step.",
    "rule": "GOV-1.3",
    "request_id": "9f0c1c0e-6a52-4c0f-b3a6-6d3a1a2c9a10"
  }
}
```

| Code | Status | Meaning |
| --- | --- | --- |
| E_VALIDATION | 400 | The body or a field fails its rule. The message names the field. |
| E_FORBIDDEN | 403 | A governance rule or a role check refused the call. `rule` names the rule. |
| E_NOT_FOUND | 404 | The report does not exist or the caller may not know it exists. |
| E_STATE | 409 | The transition is not allowed from the current state (section 3.4). |
| E_LIMIT | 422 | The base total is above 25,000.00 and cannot be routed. |

## Conflict resolution that applies

- The flag gate must sit in front of everything, including routes added later. A route added after this item that skips the gate breaks DS-1.1 and section 3.6.
- The health check path is not in the ground truth, and section 7.1 says all paths start with `/v1`. Put the health check outside `/v1`, name it in the contract file and in the pull request, and tell the Experience track.
- Section 7.1 says "a page" for the inbox and audit answers but gives no shape. Define one small shape in the contract, an `items` list and a `next_cursor`, and confirm it at the Contract freeze checkpoint.
- Migrations only move forward (section 3.6, DS-1.5). The "copy of the previous schema" test has nothing to copy until the second migration, so this migration needs the empty database test only.
