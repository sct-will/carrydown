# Repair accepted second-pass findings

Load this procedure only after presenting the completed review and recording the plan owner's decisions. It is shared by the two skills. Use the existing review report to retain evidence and repair status.

1. Present the findings and a proposed change set to the plan owner. They decide owners, dates, scope and order. A decision approving several named repairs is sufficient; do not ask again for each already approved edit. Keep rejected, deferred and pending findings visible. If the constraints are infeasible, show the options and their effects instead of silently changing the constraints.
2. Preserve the reviewed version in version control or a project-local snapshot before editing. Repair the canonical plan first, then affected specification and milestone content. Edit original ground truth only when the owner explicitly approves a source correction. Keep stable work item and milestone identifiers. Use a new identifier for new work; never reuse a retired one.
3. If an item moves between milestones, move its existing specification to the configured destination, preserve its identifier and edits, and repair relative links and the index. Then use the ground-truth skill's `scaffold_spec.py --refresh-headers` dry run, read it, and apply it. This refreshes generated headers and rationale; it does not repair all narrative content. Update affected acceptance criteria, contracts, integration points, references and the specification README as needed. For new items, preview scaffolding and write their specifications. Do not delete retired files or published issues automatically; record how the owner wants them handled.
4. Run `check_specs.py --root .` and, separately, `check_specs.py --root . --report` from an installed skill. The ordinary check must pass; `--report` alone is not a pass condition. Recalculate load, target, dependencies and checkpoints. Revisit every accepted finding and check for consequences of the repairs. Keep the original evidence and append the verification; do not erase findings to manufacture a clean report.
5. When an engineers' skill exists, preview `generate_dev_skill.py --only references`, then apply the reference refresh from the publishing skill. Review conventions separately. New or retired items may require broader regeneration; preserve hand edits to `SKILL.md` and `README.md`.
6. For an unpublished plan, finish with the plan owner's review of the repaired files and remaining risks. The ground-truth skill stops at the local handoff. Do not require GitHub access or an engineers' skill that has not been generated yet.
7. For a published plan, follow the publishing skill's repair procedure. Commit and push revised source files before updating links to them, under the existing commit and push permission rules. Preview each external change and obtain approval before its apply run. Update affected epic roll-ups, issue bodies, metadata, parent links and board values. Preserve issue numbers, human edits and unrelated labels. Never delete issues, labels, projects or repositories.
8. Stop after one review and one accepted repair cycle, then verify the affected areas. If verification exposes another substantive planning decision, present it and ask the owner to resolve it. Do not run an unbounded optimization loop or declare success with unresolved blockers. Record locally repaired, publication pending, deferred and verified states accurately.
